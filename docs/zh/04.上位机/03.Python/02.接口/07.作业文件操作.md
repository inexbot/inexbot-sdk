# 七、作业文件操作（Python）

> 本页对应 [C++ 版](../../01.C++/02.接口/07.作业文件操作.md)。**函数名与参数顺序与 C++ 完全一致**（Python SDK 由 C++ 经 SWIG 生成），差异只在两处：
>
> 1. **返回值形态**：C++ 用引用参数回填数据；Python 的返回形态由 SWIG 绑定决定，**逐接口实测**，不按类型推断。
> 2. **少数接口在 Python 中不可直接调用**（绑定缺陷），页面内已逐个标注。

本页共 47 个接口，其中 **47 个在 Python SDK 中存在**。

### job_get_all_jobfile_name

获取所有作业文件名。

```python
def job_get_all_jobfile_name(socketFd, robotsFile):
```

**返回值**：⚠️ **该接口在 Python 中不可调用**。C++ 原型的出参为`std::vector<std::vector<std::string>>&`，SWIG 未生成该嵌套容器的可用填充绑定，调用会抛 `TypeError`。请改用 C++ SDK 调用该接口。

**参数说明**（与 C++ 一致）：

| 参数 | 类型 | 说明 |
|------|------|------|
| socketFd | SOCKETFD | 连接句柄 |
| robotsFile | std::vector\<std::vector\<std::string\>\>& | 输出参数，二维数组，一维长度 4，对应 4 个机器人的作业文件列表 |

**C++ 侧返回值描述**：`SUCCESS(0)` 表示成功，负数表示失败。

## 7.9 断点与续跑

### 断点是什么

- 作业运行过程中，控制器会记录「当前作业文件 + 当前行号 + 运行上下文」，用于中断后从原位置继续。
- 断点属于**控制器侧状态**，不是上位机保存的；上位机断开连接、重启程序不会清除断点。
- 是否允许续跑，取决于断点是否仍然「有效」（见下方「旧断点失效」）。

---

### 断点清除条件

下表为现场确认口径，按触发类型分组。**固件版本不同可能有增删，升级后请以实测为准。**

**一、正常与人工操作**

| 条件 | 说明 |
| ---- | ---- |
| 作业正常运行结束 | 跑完即无断点 |
| 急停，且配置了 IO 复位 | 复位动作会清断点 |
| 在示教器上导入程序 | 覆盖作业内容 |
| 使用 `startOver=true` 从头启动 | JSON 协议重头运行见[程序运行控制](../../../05.JSON-协议/03.RTL-25.01/01.协议/03.程序/05.程序运行控制.md) |
| 回复位点 / 执行复位程序 | 现场恢复流程的一部分 |

**二、旧断点失效**（断点还在，但判定为不可恢复）

出现任一情况，控制器不再允许从旧断点续跑：

- 没有原运行上下文（控制器重启后上下文丢失）；
- 作业文件名不一致；
- 断点行号小于 1；
- 当前行所属作业与断点记录的作业不一致；
- 断点保存模式与当前模式不同；
- 调用程序或子程序被修改；
- 工艺状态不允许恢复。

**三、异常与失败**

| 条件 | 说明 |
| ---- | ---- |
| 作业打开失败、文件为空、语法错误、插补错误等异常退出 | 运行未正常建立 |
| 断点续跑计算失败或恢复超时 | 续跑请求本身失败 |

**四、配置与模式变更**

| 条件 | 说明 |
| ---- | ---- |
| 修改机型、轴映射、DH、关节参数 | 机器人对象重建，断点上下文失效 |
| 切换追加运行等特殊模式 | 与作业运行上下文不兼容 |

**五、接口主动触发**

| 条件 | 说明 |
| ---- | ---- |
| 自定义错误 `NRC_TriggerErrorReport`（**控制器侧接口**） | 会主动发送清断点命令，见[控制器 · 作业文件-指令操作](../../../06.控制器/02.接口/02.作业文件-指令操作.md) |
| 带「保留断点」语义的错误上报接口（控制器侧） | 按版本提供，是否可用见本节「版本差异与待核」 |

---

### 续跑与从头启动

| 需求 | 做法 | 说明 |
| ---- | ---- | ---- |
| 从中断位置继续 | `job_break_point_run(jobName)` | **需要运行模式**，见 §7.3 |
| 从头重新跑 | `job_run` + JSON 协议 `startOver=1` | C++ 接口无 `startOver` 参数，重头运行走 JSON 协议或先停止再运行 |
| 只跑一步 | `job_step` | 调试用，不产生可续跑断点 |

::: tip 判断能否续跑
先确认两件事：作业文件没被改过（内容/子程序）、机器人配置没动过。这两条命中「旧断点失效」或「配置与模式变更」的任一条件，续跑都会失败，直接从头跑更快。
:::

::: tip 判断能否续跑

先确认两件事：作业文件没被改过（内容/子程序）、机器人配置没动过。这两条命中「旧断点失效」或「配置与模式变更」的任一条件，续跑都会失败，直接从头跑更快。

:::

---

### 常见场景处置

| 场景 | 建议动作 |
| ---- | -------- |
| 客户现场断电后想续跑 | 控制器重启会丢上下文，按「旧断点失效」判断；不行就从头跑并检查安全点位 |
| 示教点位改了，想接着跑 | 改点位属于修改作业，断点失效，需从头运行 |
| 报错提示后作业停了，想续跑 | 若用的是 `NRC_TriggerErrorReport`，断点已被清除；改用保留断点的上报方式（按版本） |
| 换了机器人配置/换了机型 | 断点必然失效，重新运行 |
| 续跑接口返回失败 | 先用 `job_get_current_file` / `job_get_current_line` 看当前状态，再决定是否从头运行 |
