# 版本与兼容性

本文档说明纳博特控制器的 RTL 版本、SDK 版本、协议端口之间的兼容关系，帮助你在开发前选择正确的组合。

---

## RTL 版本对比

> RTL-24.03 为**稳定版本**，是当前主流出货版本。文档持续维护。

| 特性     | 说明                                                           |
| -------- | -------------------------------------------------------------- |
| 版本状态 | 稳定版，bug 修复 + 关键功能合入                                |
| 出货情况 | **当前主流出货版本**                                           |
| 通信格式 | TLV 帧（Value 段为 JSON，可读性好）                            |
| 系统功能 | 运动控制、状态、工艺、作业文件、系统配置、安全参数、协作机器人 |
| 工艺支持 | 码垛、打磨、焊接、喷涂、激光、冲压、传送带                     |
| 程序管理 | 指令级增删改查 + 远程程序启动                                  |
| 推荐场景 | 新项目开发、需要系统级功能                                     |

> 后续版本（如 2501）尚未达到稳定状态，暂未开放 SDK 文档。

### 端口体系

RTL-24.03 使用统一的端口体系，各端口用途如下：

| 端口 | 协议格式            | 用途                           | 使用者                    |
| ---- | ------------------- | ------------------------------ | ------------------------- |
| 5000 | TCP                 | **文件传输**（上传/下载/备份） | 工具、HTTP 客户端         |
| 6000 | TLV 帧（JSON 载荷） | **命令通信**，一般用于示教器   | JSON 协议用户（示教器）   |
| 6001 | TLV 帧（JSON 载荷） | **命令通信**，一般用于上位机   | C++/C#/Python SDK、上位机 |
| 7000 | TCP                 | **上位机服务功能端口**         | 上位机、工具              |

> 💡 **SDK 用户**：统一使用 **6001 端口**，无需手动切换。

## 三步确认你手上的版本组合

版本不一致是「编译能过、运行报错」类问题的第一嫌疑，动手前先确认这三处：

| 步骤 | 确认什么        | 怎么确认                                                                                                                               |
| ---- | --------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 控制器 RTL 版本 | 在示教器的系统信息页查看控制器版本（菜单路径 `[待核]`，以你的控制器版本为准）                                                          |
| 2    | SDK 包版本      | 看包内 `02-库文件/<平台>/版本信息.txt`，或程序里调用 `get_library_version()`（返回 `std::string`，**不需要连接控制器**，加载库即可读） |
| 3    | 语言运行时      | C++：MinGW 还是 MSVC（ABI 不同）；Python：精确到次版本与位数（3.10 x64 ≠ 3.11 x64）                                                    |

> 三处只要有一处对不上，先解决版本问题再看代码——否则排查方向会一直跑偏。

### 版本不匹配的典型症状

| 症状                                    | 最可能的原因                                                             |
| --------------------------------------- | ------------------------------------------------------------------------ |
| 编译通过，链接报找不到符号              | 库与编译器 ABI 不匹配（MinGW 库配了 MSVC 工程，或 32/64 位混用）         |
| 程序启动即崩、无异常信息                | 头文件与库取自不同的包（只更新了一半）                                   |
| `import nrc_interface` 报 `ImportError` | `pyd` 与 Python 版本/位数不符                                            |
| 接口能编译，但调用总是失败或命令无响应  | 库与控制器固件大版本不配套（如拿旧库连新固件）                           |
| 示教器能操作，SDK 就是连不上            | 端口/句柄用错（上位机走 6001、servoJ 走 7000），或控制器未开放上位机服务 |

### 升级 / 降级前置清单

> 以下为现场通用流程，具体菜单与导出路径随控制器版本不同，**执行前请按你的版本复核**（`[待核]`）。

1. 记录当前组合：控制器 RTL 版本、SDK 包版本、编译器/Python 版本。
2. 备份作业文件、点位、IO 配置与系统参数；确认备份能被导出并重新导入。
3. 确认目标版本的 SDK 包与工具链（MinGW / MSVC 库不通用，不能只换 DLL）。
4. 升级后跑一次最小闭环：连接 → 读状态 → 上电（状态 3）→ 单点运动 → 下电。
5. 跨大版本降级通常伴随配置不兼容，需重新配置而非简单回滚。

## SDK 版本与编译器/运行时兼容性

> **三语言接口一致**：C# 与 Python 都是对 C++ 接口的**同名同参**封装，接口语义以 C++ 文档为准；差异只在库文件形态与语言层特性（例如 Python 的 getter 返回 `[结果码, 数据]` 序列而非 `tuple`）。逐接口的平台/语言支持差异清单，`[待核]`。

### C++ SDK

| 平台    | 编译器           | ABI       | 架构        | 配置            |
| ------- | ---------------- | --------- | ----------- | --------------- |
| Windows | MinGW (GCC 8.3+) | MinGW ABI | x64         | Release / Debug |
| Windows | MSVC (VS 2019+)  | MSVC ABI  | x64         | Release / Debug |
| Linux   | GCC 8.3+         | GCC ABI   | x64 / ARM64 | Release         |

> MinGW 与 MSVC 的库 **不能混用**，必须下载对应编译器版本的 SDK。

### C# SDK

| 平台    | .NET 版本 | 架构 | 原生库                        |
| ------- | --------- | ---- | ----------------------------- |
| Windows | .NET 8.0  | x64  | 依赖对应平台的 `nrc_host.dll` |

> C# SDK 封装了 C++ 原生库，运行时须确保 `nrc_host.dll` 可被找到。

### Python SDK

| 平台    | Python 版本 | 架构 | 本地库             |
| ------- | ----------- | ---- | ------------------ |
| Windows | 待研发确认  | x64  | SDK 包内本地库文件 |
| Linux   | 待研发确认  | x64  | `_nrc_host.so`     |

> Python SDK 的本地库严格绑定 Python 版本，32 位/64 位也必须对应。

## 库与头文件必须来自同一个包

- **只换库、不换头文件**（或反过来）是最典型的「编译能过、运行崩溃」：结构体布局或函数签名变了，另一半却没更新。
- 版本依据只有一个：包内 `<语言>/RTL-xx/02-库文件/<平台>/版本信息.txt`；`get_library_version()` 读的是**运行期实际加载的库**，可用来核对「我加载的到底是不是这个包」。
- 头文件里有声明、库里没有符号的接口，说明该接口在这版库里未实现——不要按文档假定它可用（哪些接口属于这种情况，按包内头文件与库导出符号比对，`[待核]`）。
